# 优先走官方通道，官方通道缺位处才用 DOM 补丁

DSH 的插件扩展点分两类：**官方通道**（`ctx.slots` 插槽、`ctx.shortcuts`、`InputTriggerSource`、bundle patch）与 **DOM 补丁**（直接读写宿主渲染出的 DOM）。官方通道不依赖构建哈希与 DOM 结构，随上游升级更稳；DOM 补丁见效快但绑死内部实现。

我们优先官方通道。仅当上游没有暴露对应扩展点时（例如跨 tab 单一实例的文件面板），才用 DOM 补丁，且只依赖**稳定锚点**（`data-*` 属性、`class*="_后缀"`），并在插件内注释说明该补丁的兜底性质与上游开放通道后的替换方向。

锚点本身也有守卫：宿主 `data-*` 属性只在 `src/client/dom/host-anchors.ts` 拼写一次（ESLint 限制其他文件写这类字面量），`scripts/check-anchors.mjs` 再逐个到固定版本的上游树里确认它们仍然存在。补丁可以腐坏，但腐坏会变成红灯而不是静默失效。

理由：这个包按可发布标准设计（ADR-0001），而 DOM 补丁是它最容易腐坏的部分。把"何时允许 DOM 补丁"写成规矩，可以避免后来者为了方便而扩大补丁面积；把锚点收敛成一份清单，可以让"上游改名了"这件事在提交前就被发现。

## 反例：输入框引用高亮（已下线）

`0e38d7a` 移除了手打 `@` 文本的引用高亮补丁。它当时符合这里的许可：上游没有可插入的文本引用判定通道，扫描在 composer 的私有 Lexical 运行时里。但补丁只能改 DOM 外观，既分不清"选中"与"手打"，也覆盖不到发送后的消息渲染，而根因（实体节点替换导致的光标漂移）本就不在它的管辖内。

留下的教训：**DOM 补丁只能修补渲染结果，修不了产生结果的语义**。当需求是"让宿主换一种判断"，而通道又不存在时，正确结论往往是不做，而不是加倍补丁面积。
